# 캐릭터챗 웹앱 MVP — 설계

작성일: 2026-09-06

## 1. 무엇을 만드는가

번호로 미디어를 부르는 19+ 한국어 캐릭터챗 웹앱. 유저 화면 둘(피드형 대화, 리스트뷰)과
관리자 화면 하나(캐릭터 만들기 6개 탭)로 이루어진다.

DEEV(툰스퀘어)와는 **별개의 확장 서비스**다. `deev_character_gen`이 만들어 DEEV에 업로드하던
캐릭터를, 우리 플랫폼에서 직접 서비스한다. 영상(5초 움직이는 webp)이 DEEV에 없는 확장점이다.

## 2. 확정된 결정

| 항목 | 결정 |
|---|---|
| 캐릭터 공급 | 운영진 큐레이션. 유저 제작 없음 |
| 미디어 | 감정별 사전 생성. 대화 중 실시간 생성 없음 |
| 대화 모달리티 | 텍스트. TTS는 다음 사이클 |
| 코드베이스 | 새 레포. `deev_character_gen`은 제작 백엔드로 남고 코드는 복사만 |
| 등급 | 19+ |
| LLM | DGX 로컬 vLLM (무검열 Qwen3.6-35B) |
| 언어 | 한국어 |
| 계정 | 1차 없음. 결제·성인인증도 없음 |
| 관리자 잠금 | 환경변수 비밀번호 한 겹 |
| 대화 저장 | 브라우저 localStorage |
| Supabase | 별도 프로젝트. 테이블 접두사 `vt_` |

## 3. 시스템 경계

```
┌─ deev_character_gen (기존 · 제작자 전용) ──────────┐
│  캐릭터 원화 → 감정 100컷 → Wan2.2 i2v → 5초 webp  │
└──────────────────┬──────────────────────────────────┘
                   │ 사람이 관리자뷰에서 등록·업로드
                   ▼
        ┌─ Supabase (전용 프로젝트) ─┐
        │  vt_characters             │
        │  vt_admin_sessions         │
        └────────────────────────────┘
                   ▲ 읽기            ┌─ S3 + CloudFront ─┐
┌──────────────────┴─ 새 레포 ─────┐ │  {work}/{char}/…  │
│  Next.js 15 / Vercel             │ └───────────────────┘
│  /api/chat ──SSE──▶ DGX vLLM      │        ▲
│  /api/admin/* (비밀번호 게이트)   │        │ 브라우저 직결
└───────────────────────────────────┘────────┘
```

두 시스템은 코드를 공유하지 않는다. `deev_character_gen`에서 **복사**해 오는 것:

- `lib/casting/rateLimit.ts`, `apiError.ts`, `supabaseAdmin.ts`
- `lib/env.ts`
- `lib/plan/imageCodes.ts`의 `BASIC_50`, `ADULT_70`, `CODE_BY_NAME` — **목록만**, 프롬프트 본문은 두고 온다

가져오지 않는 것: `lib/workflow/*`(ComfyUI 그래프·노드 주소), `lib/plan/*` 나머지, `lib/rpc/*` 생성 핸들러.
유저 대면 서비스에 GPU 노드 주소가 딸려 들어가면 안 된다.

## 4. 데이터 모델

### vt_characters

행 하나가 캐릭터 하나. 팩은 통째로 `jsonb`에 넣고 정규화하지 않는다 —
쪼개면 제작 도구와 서비스 사이에 스키마 협상이 생긴다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | bigint identity | |
| `work_code` | text | 작품 코드. `^[a-z0-9][a-z0-9_-]{0,62}$` |
| `char_code` | text | 캐릭터 코드. 같은 정규식 |
| `pack` | jsonb | 아래 구조 |
| `published` | boolean | 기본 false |
| `sort_order` | int | 리스트 정렬 |
| `created_at` / `updated_at` | timestamptz | |

`(work_code, char_code)` 유니크.

### pack 구조

```jsonc
{
  "name": "호시",
  "intro": "야근이 끝나도 굳이 같은 지하철을 타는 회사 후배.",
  "template": "기본",
  "characterInfo": "#캐릭터\n이름 : 호시\n외모 : …\n성격 : …",
  "prologue": "*사무실 불이 하나둘 꺼진다.*\n호시 | …",
  "background": "같은 팀에 온 지 반년.",
  "firstMedia": { "kind": "motion", "n": 1 },   // 없으면 null
  "loreBooks": [{ "title": "…", "keywords": ["…"], "content": "…" }],
  "genre": "Romance",
  "target": "남성",
  "rating": "free",                              // safe | free(19+)
  "tags": ["직장후배", "존댓말"],
  "have":  [1, 2, 9, 12, 14, 18, 31, 36, 46],    // 정지 이미지가 있는 번호
  "haveMotion": [1, 2, 18, 31, 46]               // 영상이 있는 번호
}
```

`have` / `haveMotion`은 업로드 시 서버가 갱신한다. 사람이 손으로 적지 않는다.

### vt_admin_sessions

관리자 비밀번호 통과 시 발급하는 토큰. `token` PK, `expires_at`. TTL 24시간.

RLS는 모든 테이블에 켜고 정책을 두지 않는다 = anon 키로 접근 불가.
서버 라우트(service_role)만 읽고 쓴다.

## 5. 미디어 주소 규칙

```
{CDN}/{work_code}/{char_code}/{n}.webp        정지 이미지
{CDN}/{work_code}/{char_code}/m/{n}.webp      움직이는 webp (81프레임 · 16fps · 5초)
```

**번호의 뜻은 캐릭터마다 다르다.** 처음에는 모든 인물이 같은 120칸 표를 쓴다고 가정했으나,
실제 업로드는 인물마다 칸 수도 뜻도 다르고 수시로 바뀐다(윤세린은 169칸, 착의 73 + 탈의 96).
고정 표를 씌우면 모델은 「2번 미소」를 부르는데 화면에는 다른 장면이 뜬다.
그래서 뜻은 팩의 `codes`가 직접 들고 있고, `imageCodes.ts`는 새 캐릭터를 만들 때 쓰는
기본 템플릿으로만 남는다. `codes`는 서버 전용이다 — 브라우저는 번호를 주소로 바꾸기만 하면 된다.

**해석 규칙 한 줄:** `haveMotion`에 있으면 `m/{n}.webp`, 아니면 `{n}.webp`.
유저 설정도, 서버 상태도 없다. 캐릭터마다 영상 수가 다른 것이 정상이다.

## 6. 대화 한 턴

1. 브라우저가 `/api/chat`에 `{ workCode, charCode, message, history[] }`를 POST.
   `history`는 localStorage에 있던 최근 N턴(기본 12턴).
2. 서버가 rate limit 확인 → `vt_characters`에서 팩 조회 → 시스템 프롬프트 조립.
3. DGX vLLM에 OpenAI 호환 `/v1/chat/completions` 스트리밍 요청.
4. 토큰을 SSE로 그대로 흘려보낸다.
5. 브라우저가 스트림 앞머리에서 번호를 뽑아 무대를 갈고, 나머지를 자막에 흘린다.

### 시스템 프롬프트 조립

```
[캐릭터 정보]      pack.characterInfo
[배경 상황]        pack.background
[출력 규칙]        응답은 반드시 번호 하나로 시작한다. 예: "31 저는… 그냥, 기다렸어요."
[감정 코드]        have에 있는 번호만 나열 — "1기본 2미소 9경청 …"
[로어북]           키워드가 이번 턴 입력에 나온 항목만
```

**코드표에는 `have`에 있는 번호만 싣는다.** 없는 번호를 모델이 부르면 빈 화면이 된다.
로어북은 키워드 매칭으로 해당 턴에만 실어 토큰을 아낀다 — 검증된 방식이다.

### 번호 파싱

응답 첫 토큰들에서 `^\s*(\d{1,3})\s` 를 찾는다. 못 찾으면 직전 번호를 유지한다.
파싱 실패가 화면을 비우면 안 된다.

## 7. 화면

### A. 대화 (시작 화면)

세로 전체화면 9:16. 미디어가 배경이 아니라 무대다.

- 상단: `☰`(리스트 열기) · 캐릭터 이름. 위아래 스크림은 자막 가독성을 위한 필수 장치
- 자막: 현재 대사 한 줄 크게, 직전 대사 한 줄 흐리게. **스크롤되는 로그가 아니다**
- 우측 레일: 기록 서랍
- 하단: 입력창 + 보내기
- 위로 밀면 다음 캐릭터

자막 배치를 고른 이유는 음성 대비다. 말풍선 스레드는 TTS를 켤 때 화면을 다시 짜야 한다.

### B. 리스트뷰

좌상단 `☰`에서 여는 대등한 화면. 카드에 썸네일(`m/1.webp` 있으면 그것), 이름, 소개, 태그, 컷 수.

### C. 관리자 — 캐릭터 만들기 (6개 탭)

DEEV의 기존 화면을 그대로 옮긴다. 탭 순서: 프로필 · 캐릭터 설정 · 시작 설정 · 미디어 · 로어북 · 등록.
우측에 대화 미리보기 패널. 하단 이전/다음(마지막은 등록).

달라지는 곳은 둘뿐이다:

- **시작 설정 → 첫 미디어**: 움직이는 webp도 받는다
- **미디어 탭**: 폴더 칩에 `영상(n)`이 하나 늘고, 주소에 `m/`가 붙는다

나머지 네 탭은 손대지 않는다.

## 8. 업로드

`deev_Fileupload`와 같은 양식이다.

1. 폴더를 드롭 → 폴더명 = 캐릭터, 파일명 = 상황(`호시_두근_01.webp`)
2. 상황 이름을 `CODE_BY_NAME`에서 찾아 번호를 붙인다. **표에 없으면 막는다** —
   짐작해서 번호를 주면 그 번호의 뜻이 캐릭터마다 달라지고, 조용히 틀린다
3. `/api/admin/sign-upload`가 S3 키를 **서버에서** 조립해 presigned PUT을 내준다.
   클라이언트는 캐릭터·상황·확장자만 보낸다
4. 업로드 성공분을 `pack.have` / `pack.haveMotion`에 반영

한 번에 500개 상한. 확장자는 `webp`만.

## 9. 이번 사이클 밖

계정·로그인 · 결제·PG·성인인증 · TTS · 장기 기억/요약 · 탐색·랭킹 · 유저 제작 ·
관리자 계정과 권한(비밀번호 한 겹으로 대신) · 실시간 영상 생성.

## 10. 검증

- **순수 함수 우선**: 번호 해석(`resolveMedia`), 파일명 → 계획(`planUploads`), 프롬프트 조립,
  번호 파싱은 I/O 없이 테스트한다. 여기가 조용히 틀리는 곳이다
- **경계값**: `have`에 없는 번호, 표에 없는 상황 이름, 영상 0개 캐릭터, 파싱 실패
- 화면은 실제로 띄워 확인한다 — 자막 가독성과 스크림은 눈으로만 판단된다

## 11. 가정

미결이었으나 확인 없이 기본값으로 진행한 것:

- 관리자 잠금은 환경변수 비밀번호 한 겹. 관리자가 늘면 계정으로 승격한다
- 대화는 브라우저에만 남는다. 기기를 바꾸면 사라진다
- Supabase는 전용 프로젝트. 제작 도구와 유저 대면 서비스를 격리한다
